Automatic uniqueness validation

Current result: NOT RUN. There is no candidate surface, candidate TIFF, official sample template, or complete canonical registry manifest in this checkout. The nine-site focus audit is not the full registry and cannot clear a future candidate.

What the checker evaluates

  • Before placement: maximum absolute Spearman rank-correlation between the continuous candidate surface and every registry surface, on the common official template footprint. The run fails if any |rho| > 0.90.
  • After placement: for each registry dot raster, the fraction of candidate positive cells within Euclidean distance ≤3 pixels of a registry positive cell. The run fails if any fraction is >70%.
  • All entries: exact grid match, single-band rasters, and SHA-256 verification for both each registry surface and dot raster. No resampling, selection, or lattice exemption is implemented.
  • Fail-closed manifest: requires an explicit completeness claim, a version and source, all nine focus-site winner IDs, and at least one literal-lattice ID.

Prepare a local complete registry manifest

Use the canonical shared template's refreshed registry export—not only these nine historical winners. Keep all input rasters local and ignored by Git. Every entry must supply the exact surface file, final-dot file, and SHA-256 for both.

{
  "schema_version": 1,
  "registry_version": "canonical-version-or-commit",
  "source": "canonical shared-template registry location",
  "complete": true,
  "includes_literal_lattice": true,
  "includes_all_focus_site_winners": true,
  "entries": [
    {
      "id": "GEMSDOE24-registry-record",
      "surface_file": "rasters/GEMSDOE24-surface.tif",
      "surface_sha256": "64-character SHA-256",
      "dots_file": "rasters/GEMSDOE24-dots.tif",
      "dots_sha256": "64-character SHA-256"
    },
    {
      "id": "r13-lattice-s5",
      "surface_file": "rasters/r13-lattice-s5-surface.tif",
      "surface_sha256": "64-character SHA-256",
      "dots_file": "rasters/r13-lattice-s5-dots.tif",
      "dots_sha256": "64-character SHA-256"
    }
  ]
}

The example omits most rows and is explanatory only; it is not a usable manifest. In the actual file, each registry raster pair has a distinct ID. At minimum include IDs containing `GEMSDOE24`, `GEMSDOE25`, `GEMSDOE27`, `GEMSDOE28`, `GEMSDOE30`, `GEMSDOE31`, `GEMSDOE32`, `GEMSDOE33`, and `GEMSDOE36`, plus the literal lattice. The completion flags must be backed by the canonical source/version and a reproducible inventory.

Run and interpret

python scripts/validate_submission.py candidate.tif \
  --template data/sample_submission.tif \
  --labels data/labels.tif \
  --out reports/preflight.json
python scripts/validate_registry_uniqueness.py \
  --surface candidate-surface.tif \
  --candidate candidate.tif \
  --template data/sample_submission.tif \
  --registry-manifest data/registry/manifest.json \
  --out reports/uniqueness.json

The uniqueness report describes comparisons against every manifest entry. It cannot independently discover a raster omitted from the manifest, so it records that completeness is asserted by the manifest and not independently verified. It never sets submission_authorized=true. The shared holdout, leakage canary, official score receipt, independent slot selector, and reviewer-approved registry provenance remain separate gates.

Local file placement guidance is in the repository's data/registry/README.md (that local-only file is not served by GitHub Pages). The historical focus-site-only comparison is in focus-site-audit.json.
